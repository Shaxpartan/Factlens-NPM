# FactLens SDK and CLI v6.5.0 Design

## Goal

Bring the Node.js/TypeScript SDK and CLI to parity with the current FactLens Verify API, expose saved API-key customization through developer-token management routes, and make terminal progress/timing truthful and polished.

## SDK contract

- Version exactly `6.5.0`.
- Preserve existing public SDK calls and millisecond `RequestOptions.timeout`.
- Add `timeoutSeconds`; using both timeout forms is a configuration error.
- Progress events retain `elapsedMs` and add `elapsedSeconds`, measured with a monotonic clock.
- Verify types include `verdictColor`, complete multi-claim results, `failed_claims`, no-claim messages, request-level verdict colors, and current source/result structures.
- Request-level Verify supports the current source, instruction, search, media/transcript, and verdict override fields.

## Saved API-key customization

Public developer-token routes manage the same key-scoped storage used by the dashboard, never a parallel SDK-only configuration:

- `GET /v1/projects/:projectId/keys/:keyId/customization`
- `PATCH /v1/projects/:projectId/keys/:keyId/customization/preferences`
- `PUT|DELETE /v1/projects/:projectId/keys/:keyId/customization/prompts/:mode/:stage`
- `PUT|DELETE /v1/projects/:projectId/keys/:keyId/customization/verdicts`

Every route checks developer-token account status plus project/key ownership. Preferences preserve omitted lists, normalize domains, allow explicit empty lists, and make blocked domains win overlap. Prompt configuration uses the existing canonical normalization contract with an 8,000-token default and 2,000–20,000 range in 100-token increments. Verdict configuration uses the existing v3 stable-ID/name/color/rule contract.

The SDK exposes these routes as `client.keys.customization.get`, `updatePreferences`, `savePrompt`, `resetPrompt`, `saveVerdicts`, and `resetVerdicts`.

## CLI Verify surface

Human and JSON modes retain the same underlying SDK client. The CLI adds current Verify controls including instructions, search query/result count, audio URL, transcript/transcript file, language, request verdict JSON, and explicit empty source-preference overrides. Image file support aligns with the API: PNG, JPEG, WebP, HEIC, and HEIF.

Human Verify output renders all successful claims and per-claim failures separately. The API-provided `verdictColor` is authoritative: color-capable terminals use 24-bit ANSI; with ANSI disabled, the hex value remains visible. `--quiet` prints verdict IDs, `--verbose` exposes full source URLs/diagnostics, and `--json` remains machine-readable API output.

## Progress design A

Interactive TTY progress uses one in-place line via carriage-return/line-clear terminal control sequences. It never creates the stacked preview artifact and never moves backward.

- Text: Sent → Verifying → Result.
- Image: Image loaded → Verifying image → Result.
- Audio: Prepared → real upload percentage → Transcribing → Verifying → Complete.
- Active rail/spinner: cyan.
- Completed phases: green.
- Waiting/retry states: warning colors.
- Final verdict: exact API `verdictColor`.
- `NO_COLOR`: no ANSI.

Text and image do not display invented percentages. Audio upload percentage is computed only from acknowledged TUS byte offsets. Completed phases are monotonic and cannot regress when the transport reconnects or emits an earlier state.

Non-TTY output avoids animation frames entirely.

## Timing

Client elapsed time begins before local preparation/upload and ends after the final Verify response. It uses a monotonic clock so system clock changes cannot make elapsed time move backward. Human output distinguishes total client wall time from server `response_time_ms`.

CLI keeps `--timeout MS`, adds `--timeout-seconds SEC`, and adds `--time-unit auto|ms|s` for presentation.

## Safety and compatibility

- No Extension, Console, Website/Admin, or Support changes.
- Existing dashboard-saved settings continue to affect Verify automatically.
- Request-level source/verdict overrides remain request-scoped and do not mutate saved configuration.
- Management mutations retain request-ID/idempotency semantics.
- No npm publication is performed as part of implementation unless separately requested.
- API routing changes are kept behind the existing signed developer-token platform gateway; no Netlify redirect change is required.
