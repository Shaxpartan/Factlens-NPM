# FactLens NPM v6.7.0 Runtime Integration Design

Date: 2026-08-17

## Goal

Ship FactLens NPM **v6.7.0** as the advanced SDK/CLI companion to the unified `/v1/verify` runtime. Preserve the convenient v6.5.0 verification API while exposing precise transport/runtime timing, stronger diagnostics, richer request inspection, improved audio lifecycle visibility, and complete compatibility with any additive API contract changes introduced by the runtime refactor.

## Release boundary

This release targets the `Shaxpartan/Factlens-NPM` repository only. API routes/headers required by the SDK are implemented and documented in the coordinated FactLens API runtime release.

Version must be `6.7.0` in package metadata, lockfile, SDK/CLI request headers, CLI `--version`, README examples, changelog, release tests, and packed artifacts.

## Compatibility

Existing v6.5.0 code must continue to work:

```ts
const result = await factlens.verify({ text: '...' });
```

Existing CLI Verify commands and v6.5.0 options remain valid. New timing/diagnostic surfaces are additive.

Do not make ordinary users consume transport metadata to obtain a verdict. Advanced metadata should be available explicitly and should power the CLI internally.

## SDK response metadata architecture

Introduce a transport/runtime metadata type separate from verdict/result data:

```ts
export interface FactLensServerTiming {
  authMs?: number;
  customizationMs?: number;
  coreMs?: number;
  postprocessMs?: number;
  edgeMs?: number;
}

export interface FactLensResponseMeta {
  requestId?: string;
  clientTotalMs: number;
  clientTotalSeconds: number;
  serverTiming: FactLensServerTiming;
  gatewayNetworkMs?: number;
  retryAfterMs?: number;
  httpStatus: number;
}

export interface DetailedResponse<T> {
  data: T;
  meta: FactLensResponseMeta;
}
```

`gatewayNetworkMs` is an estimate calculated only when both `clientTotalMs` and `edgeMs` are present:

```text
max(0, clientTotalMs - edgeMs)
```

Label it clearly as client/network/gateway remainder; never present it as exact Netlify time.

### SDK methods

Keep:

```ts
client.verify(input, options?) -> Promise<VerifyResponse>
```

Add:

```ts
client.verifyDetailed(input, options?) -> Promise<DetailedResponse<VerifyResponse>>
```

The same request execution path powers both methods; `verify()` returns `.data` and does not make a second request.

Apply the detailed-response pattern to read-only management/request operations where useful, especially usage and request inspection.

## Server-Timing parser

Parse the standard `Server-Timing` header returned by the new API shell. Parsing requirements:

- case-insensitive metric names;
- tolerate unknown metrics;
- ignore malformed/non-finite durations;
- preserve decimal milliseconds;
- do not throw if the header is absent;
- map known metrics `auth`, `customization`, `core`, `postprocess`, `edge` to typed fields.

Expose raw unknown metrics only in an advanced metadata map if doing so does not destabilize the public type contract.

## Accurate client timing

Continue using a monotonic client clock. Timing starts before SDK-side upload/preparation relevant to the requested operation and ends only after the final HTTP body is consumed.

Do not call the API's `response_time_ms` the full server time when the new `edge` metric is available. Terminology becomes:

- `Total`: SDK/client wall time;
- `Edge`: full Supabase Edge invocation time;
- `Core`: verification pipeline time;
- `Auth`;
- `Customization`;
- `Post`;
- `Network/Gateway`: computed remainder, explicitly approximate.

Milliseconds and seconds remain available. Existing `timeout` milliseconds and v6.5.0 `timeoutSeconds` remain compatible.

## CLI timing presentation

Default human result output should be concise:

```text
Timing   6.18s total · 4.02s core
```

When meaningful non-core timing exists, show a compact second line:

```text
Runtime  0.42s auth · 0.18s config · 4.02s core · 0.11s post · 5.03s edge
Outside  ~1.15s network/gateway
```

`--verbose` shows the full breakdown automatically.

Add `--trace` as an explicit diagnostic mode that includes:

- request ID;
- total/client duration;
- every known `Server-Timing` metric;
- approximate client/network/gateway remainder;
- retry/poll count where relevant;
- provider-independent lifecycle phases emitted by the SDK;
- no API key or developer-token secret.

`--json` emits stable structured timing metadata rather than ANSI-formatted strings.

## Progress Design A remains authoritative

Retain the v6.5.0 forward-only colored phase rail. Do not reintroduce bouncing or fake server percentages.

Colors:

- active spinner/rail: cyan;
- completed phase: green;
- wait/retry: yellow/orange;
- terminal error: red;
- verdict: exact API `verdictColor` using truecolor ANSI;
- `NO_COLOR`: no ANSI, but retain textual state and hex verdict color.

For text/image, progress stays phase-based because the API does not stream exact pipeline percentage.

## Audio/video lifecycle upgrade

Audio is where v6.7.0 should become substantially more informative.

Track explicit client lifecycle phases:

1. prepare;
2. upload;
3. transcription submitted;
4. waiting/polling;
5. verification resumed;
6. complete.

Progress events should expose:

```ts
interface AudioLifecycleProgress extends ProgressEvent {
  phase: 'prepare' | 'upload' | 'transcription' | 'waiting' | 'verifying' | 'complete';
  phaseElapsedMs: number;
  pollCount?: number;
  nextPollInMs?: number;
  uploadedBytes?: number;
  totalBytes?: number;
  uploadPercent?: number;
}
```

Continue honoring server `Retry-After`/poll hints. Do not poll faster than requested. Do not treat waiting time as core verification time.

Final audio timing should make clear, for example:

```text
Timing   18.4s total · 6.1s transcription/wait · 5.0s edge resume · 3.9s core
```

Only print phase values actually measured or supplied by the API.

## Request inspection SDK

Make request inspection a polished typed surface rather than raw JSON-first output.

Expose a normalized request-detail type matching the API's fast detail DTO:

```ts
interface RequestDetail {
  requestId: string;
  createdAt: string;
  mode?: string;
  status: string;
  timing?: FactLensServerTiming;
  results: VerifyResult[];
  failedClaims: FailedClaim[];
  usage?: UsageSummary;
  error?: { code?: string; message?: string };
}
```

The SDK should retain source URLs/titles/domains, verdict ID/name/color, confidence, evidence strength, explanation, and claim text.

Do not add deprecated `Input` or `Pipeline` presentation concepts to the CLI request-detail command.

## CLI request detail design

`factlens request <request-id>` and any equivalent logs-detail command should render the same result language as Verify:

```text
Request  <id> · complete · TEXT

01  ● TRUE
    HIGH confidence · STRONG evidence
    Claim text...

    Explanation...

    Sources
    1  Reuters — reuters.com
    2  Official source — example.gov

Timing   6.18s total/core metadata where available
```

Multiple verdicts render as separate colored cards/sections. Partial failed claims render after successful results.

`--json` returns the unstyled normalized DTO.

## Customization management parity

Keep and harden the v6.5.0 `client.keys.customization.*` API and matching CLI commands.

v6.7.0 requirements:

- read/write/reset Preferences;
- read/write/reset Prompts for text/audio/image supported stages;
- read/write/reset Verdicts including custom stable IDs, rules and colors;
- preserve partial Preferences updates without erasing the other list;
- expose revisions/timestamps returned by the API;
- support `AbortSignal` and detailed response metadata on management operations;
- show human-readable diffs/summaries in CLI after writes;
- retain `--json` for automation.

## AbortSignal and transport control

Add `signal?: AbortSignal` to request options across Verify and management/read operations. Compose it safely with timeout cancellation; whichever aborts first wins and listeners/timers are cleaned up.

If the SDK supports custom fetch injection, preserve it. If not, do not add an unnecessary new abstraction solely for this release.

## Read-only retry policy

For idempotent/read-only SDK operations such as usage, request detail, logs and customization GET:

- retry once on network failure or 502/503/504;
- use short jittered delay;
- respect `Retry-After` when it is short and valid;
- expose retry count in detailed metadata/trace.

Do **not** automatically retry mutation requests or billable Verify POSTs unless the existing idempotency contract explicitly proves the retry is safe with the same request ID. Default v6.7.0 behavior remains conservative.

## Doctor command

Add a non-billable CLI diagnostic command:

```text
factlens doctor
```

It should use `/v1/usage` or another non-billable authenticated read and report:

- SDK/CLI version;
- API reachability;
- authentication validity;
- HTTP status;
- total client timing;
- available Server-Timing breakdown;
- approximate network/gateway remainder;
- whether ANSI truecolor is available;
- whether `NO_COLOR` is active.

Never print the API key.

`factlens doctor --json` returns a machine-readable diagnostic object.

## Error model improvements

Extend SDK errors with safe transport diagnostics:

```ts
class FactLensError extends Error {
  code?: string;
  status?: number;
  requestId?: string;
  retryAfterMs?: number;
  meta?: FactLensResponseMeta;
}
```

Secrets, raw authorization headers and uploaded binary payloads must never be included in error serialization.

## CLI output discipline

Human output should be concise by default. Use:

- normal mode: verdict/result + concise timing;
- `--verbose`: sources, usage, detailed timing and request metadata;
- `--trace`: transport/runtime diagnostics;
- `--quiet`: minimal verdict/result suitable for shell use;
- `--json`: stable machine-readable output.

Avoid dumping raw API JSON in normal human mode.

## Success criteria

- Package version is 6.7.0 everywhere.
- Existing v6.5.0 `verify()` usage remains valid.
- SDK can distinguish client total, Edge total, core verification and individual runtime-shell phases when the API supplies them.
- CLI no longer labels core verification time as the entire server time.
- Audio waiting/poll/resume time is visible and not conflated with the core pipeline.
- CLI result/request detail uses exact verdict colors and complete result cards.
- `factlens doctor` provides useful non-billable latency diagnostics without leaking secrets.
- All release tests pass on Node 18/20/22.
- No package publish occurs until the coordinated API runtime is production-compatible and the user explicitly chooses to publish.
